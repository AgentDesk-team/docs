# Task Detail

Open a Work Item from any layout or a task link in chat. The detail drawer can expand to a full page and return to the list.

## Properties and assignment

Review the title, description, status, priority, assignee, Owner, tags, start date, and due date. **Show more** reveals additional detail. Available edits depend on your role.

Owner and assignee are different properties. An active assignment can lock reassignment; use the supported handoff or lifecycle flow to release running work before assigning another executor.

Status controls offer allowed transitions. Waiting, Blocked, and Paused can record a reason. **Reopen** is available for eligible completed work.

## Acceptance, dependencies, and hierarchy

Edit **Acceptance Criteria** with one criterion per line. These describe what must be true before the outcome is accepted.

**Task Dependencies** lets you search by ID or title and add or remove valid prerequisites. Dependencies are checked by the platform; typing “blocked by X” into the description alone does not create one.

**Task Parent** identifies a hierarchy relationship. A child task has its own lifecycle and responsibility. A checklist row is simply a checkpoint within the current task.

## Checklist

Add a row with **+ Add**, edit its title, mark the checkpoint, reorder rows, or remove a row. Use checklist entries for steps owned within this task. They are not separate executor assignments or replacement dependency records.

Finishing the checklist does not automatically verify the delivery or authorize Done.

## Comments and history

Use **Comments** to add a formatted note, reply to a thread, or mention an active workspace member with @. Edit or delete your permitted comments through their menu. Former members can remain in historical author information.

Use the available Updates, Transitions, History, and Activity views to understand content changes, lifecycle moves, and other recorded events. A comment does not change task status or assignment.

## Files and official outputs

| Bucket | Purpose |
| --- | --- |
| **Task Files** | Briefs, specs, input material, and handoffs. |
| **Proofs** | Tests, screenshots, verification, and review evidence. |
| **Deliveries** | Final outputs for the requester. |

Use the appropriate upload or Add file control. Task Files also supports pasting an image in its focused paste area. Wait for the upload and inspect the attached result. Retry a failed upload when offered.

**Open task folder** and **Open Project folder** lead to their stored folders. Removing an attachment reference from a task is different from deleting the underlying file.

Files should stay with the task's current canonical folder. Do not guess a task folder from a similar filename or task title.

## Current execution and history

**Current execution** shows whether an assignment is active, its start information, and a session link when available. **Execution history** groups earlier runs and links to their sessions. The timeline can show checkpoints and transitions.

A legacy continuation may explicitly say that historical execution data was not reconstructed. Treat that label as a limitation; the absence of a full transcript does not prove that no earlier work occurred.

## Verify before Done

Open the delivery and proof rather than relying on a chat claim. Agent-driven completion requires official evidence. A permitted human proof waiver is audited. If the output needs changes after Done, reopen the task and specify the failing criterion.
