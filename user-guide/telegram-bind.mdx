# Telegram bot binding

Telegram binding connects one AgentDesk agent to one Telegram bot from the Dashboard Chat Panel.

The setup is a multi-step flow. Connecting the bot validates and saves the bot identity, but Telegram chat routing may need one more setup step before live messages sync correctly.

## Before you start

You need:

- A Telegram account.
- A Telegram bot token from BotFather.
- Permission to manage the workspace or the agent.
- Access to the AgentDesk workspace gateway restart action if the UI says runtime sync is not active yet.

<Note>
You usually do not need to find or type your numeric Telegram user ID manually. After you message the bot, AgentDesk can detect the latest Telegram user from runtime evidence, pairing data, or pending Telegram updates.
</Note>

## Create a Telegram bot and get the token

Telegram bots are created through Telegram's official **BotFather** account.

1. Open Telegram.
2. Search for `@BotFather`.
3. Open the verified BotFather chat.
4. Send:

   ```text
   /newbot
   ```

5. BotFather asks for a display name. Enter a human-readable name, for example:

   ```text
   AgentDesk Support Bot
   ```

6. BotFather asks for a username. Enter a unique username that ends with `bot`, for example:

   ```text
   agentdesk_support_bot
   ```

7. After the bot is created, BotFather returns a bot token. It looks similar to:

   ```text
   1234567890:AAExampleTokenValueDoNotUse
   ```

8. Copy the token. You will paste it into AgentDesk when binding the agent.

<Warning>
Treat the bot token like a password. Do not post it in chat, screenshots, tickets, docs, or logs. Anyone with the token can control the bot until the token is revoked or rotated in BotFather.
</Warning>

Optional BotFather commands:

- `/mybots` — view and manage your bots.
- `/setdescription` — set the bot description shown in Telegram.
- `/setuserpic` — set the bot avatar.
- `/revoke` — revoke the current token and generate a new one if the token is exposed.

## Bind an agent to Telegram

1. Open the AgentDesk Dashboard.
2. In the Chat Panel, select the agent you want to bind.
3. Click the Telegram status chip in the Chat Panel header.
   - It may show `Telegram · Not connected`, `Telegram · @botname`, or `Telegram · Error`.
4. In the Telegram Bot dialog, paste the bot token.
5. Click **Connect Telegram**.
6. Confirm the bind action.
7. Wait for token validation.

If successful, AgentDesk saves the connected bot identity and shows the bot username.

The raw bot token is not shown again after save.

<Note>
After a bot is connected, the dialog no longer shows **Connect Telegram**. The available actions are **Unbind** and **Test connection**.
</Note>

## Finish Telegram user detection

After the bot is connected, AgentDesk needs to know which Telegram user should be allowed to chat with the bound agent.

1. In the Telegram Bot dialog, click **Send a DM to the bot**.
   - This opens Telegram directly for the connected bot.
2. Send any message to the bot from the Telegram account you want to use with AgentDesk.
3. Return to the AgentDesk Telegram Bot dialog.
4. Click **Detect latest Telegram user**.

AgentDesk attempts to detect the Telegram user from runtime evidence, pairing data, or pending Telegram updates. If detection succeeds, AgentDesk saves the detected `telegram_user_id` for the workspace routing config.

At this point, routing is saved. That does not always mean live Telegram sync is active immediately in the running workspace gateway.

## Apply runtime sync if needed

In some cases, the workspace gateway is already using the latest Telegram routing config. In other cases, the UI may show a warning that runtime sync is not active yet.

If the dialog shows a restart warning or restart call-to-action, restart the workspace gateway from the UI.

After restart completes, the expected success message is:

```text
Workspace gateway restarted. Telegram is successfully bound.
```

<Warning>
Do not assume every bind requires a gateway restart. First connect the bot, send a DM, detect the Telegram user, and follow the UI warning. Restart only when AgentDesk says the current runtime has not applied the saved routing yet.
</Warning>

## Test the connection

After an agent is connected:

1. Open the Telegram Bot dialog again.
2. Click **Test connection**.

The current test checks the saved binding and bot identity. Token validation uses Telegram `getMe`; it does not send a Telegram message by itself.

## Chat through Telegram

Expected user flow:

1. Create a Telegram bot in BotFather and copy the token.
2. Bind the bot token to an AgentDesk agent.
3. Click **Send a DM to the bot** and send a Telegram message to the bot.
4. Click **Detect latest Telegram user** in AgentDesk.
5. If AgentDesk warns that runtime sync is not active, restart the workspace gateway from the UI.
6. Send a message to the bot in Telegram.
7. OpenClaw routes that Telegram message to the bound AgentDesk agent.
8. The agent reply is sent back through the Telegram bot.

When routing is active, the Dashboard can use the runtime Telegram direct-session format:

```text
agent:<agent_id>:telegram:<account_id>:direct:<telegram_user_id>
```

This lets the Chat Panel switch to the same Telegram-linked session used by live Telegram inbound messages.

## What is implemented now

Implemented behavior:

- Chat Panel Telegram status chip.
- Bind dialog from Chat Panel.
- Bot token validation through Telegram `getMe`.
- One bot cannot be bound to multiple AgentDesk agents/workspaces.
- Binding state is stored server-side and exposed as redacted public metadata.
- Agent roster/contact metadata updates after bind.
- OpenClaw profile Telegram account/binding config updates after bind.
- **Send a DM to the bot** opens Telegram directly for the connected bot.
- **Detect latest Telegram user** can save workspace Telegram routing from runtime evidence, pairing data, or pending Telegram updates.
- After successful detection, routing is saved; runtime sync may still require a workspace gateway restart.
- If runtime sync is not active, the UI shows a warning and restart call-to-action.
- After a successful gateway restart, the UI confirms that Telegram is successfully bound.
- After a bot is connected, **Connect Telegram** is hidden; **Unbind** and **Test connection** remain available.
- Unbind endpoint and UI button exist, even though unbind/rotate was originally outside the first MVP scope.

Current limitations:

- Telegram binding is optimized for the one-workspace-user happy path.
- Multi-user Telegram bot routing is not fully generic yet.
- `getMe` validation proves the token and bot identity; it does not prove a full inbound/outbound Telegram conversation by itself.
- Saved routing may require workspace gateway restart before live Telegram sync is active.
- If the Dashboard process is serving old code, reload may be needed before new bind/session behavior appears.

## Error states

You may see these errors:

- **Invalid token format** — the token does not match Telegram bot token format.
- **Telegram rejected this bot token** — Telegram `getMe` rejected the token.
- **Telegram provider unavailable** — AgentDesk could not reach Telegram during validation.
- **Bot already bound** — the Telegram bot is already connected to another AgentDesk agent/workspace.
- **Agent not found** — the selected agent does not exist or is disabled.
- **No connected Telegram binding** — test was attempted before a successful bind.
- **No Telegram user detected** — AgentDesk has not seen a usable Telegram DM/update for this bot yet. Click **Send a DM to the bot**, message the bot in Telegram, then try detection again.
- **Routing saved but runtime sync pending** — AgentDesk saved the detected Telegram user, but the running workspace gateway has not applied the routing yet. Follow the restart call-to-action if shown.

## Security notes

- Bot token is accepted through a password field.
- The raw token is not returned by read APIs.
- Public binding metadata contains bot identity, status, account ID, deep link, and linked session key only.
- The saved token is written into the OpenClaw profile Telegram account config so the Telegram provider can use it.
- Binding changes are logged/audited without exposing the raw token.
- Detected Telegram user routing is saved as workspace configuration; do not share screenshots that expose private user/account identifiers if that is sensitive for your workspace.
