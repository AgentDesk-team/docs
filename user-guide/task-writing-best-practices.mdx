# Write clear tasks for agents

A good AgentDesk task gives the agent enough context to make progress without guessing, while staying small enough to verify.

Use this guide when you ask an agent to create a task from chat or when you refine a follow-up request.

<Note>
In the current AgentDesk product, task creation is supported through chat with an agent. Prefer the **Agent Product Owner** when you want to turn a request into a clear task.
</Note>

## Quick rule

A good task answers five questions:

1. **What outcome do you want?**
2. **Why does it matter?**
3. **What is in scope and out of scope?**
4. **What should the final output look like?**
5. **How will you verify it is done?**

If one of these is missing, the agent may still work, but the output is more likely to be incomplete, overbuilt, or hard to review.

## Recommended task format

Use this structure:

```text
Title:
Short action-oriented name.

Goal:
What user/business outcome should change?

Context:
Why are we doing this? What prior decision, file, customer issue, or task does it relate to?

Scope:
What should the agent do?

Out of scope:
What should the agent not touch?

Inputs / references:
Links, files, examples, screenshots, prior task ids, user quotes, APIs, docs.

Expected output:
What artifact should be delivered? Examples: UI change, spec, PR, screenshot proof, CSV, report, docs page.

Acceptance criteria:
Bullet list of observable pass/fail checks.

Verification required:
How should the agent prove it works? Examples: Playwright UI E2E, unit tests, screenshot, build, lint, manual live check.

Owner / reviewer:
Who should review or approve?
```

## Good example

```text
Title:
Add Telegram bot binding guide to User Guide docs.

Goal:
Users should understand how to connect an AgentDesk agent to a Telegram bot and what limitations exist.

Context:
TASK-073 implemented Telegram bot binding from the Chat Panel. The internal delivery guide exists, but public docs need a User Guide page on docs.agentdesk.team.

Scope:
- Add a Mintlify MDX page under User Guide.
- Explain prerequisites, bind steps, test connection, chat-through-Telegram flow, limitations, and error states.
- Add the page to docs navigation.
- Publish to the canonical docs repo.

Out of scope:
- Do not change product code.
- Do not document unimplemented multi-user routing as available.

Inputs / references:
- TASK-073 spec and implementation notes.
- Nam's confirmation about current Telegram session behavior.
- Canonical docs repo: AgentDesk-team/docs.

Expected output:
- New docs page: user-guide/telegram-bind.mdx.
- Updated docs.json navigation.
- Commit pushed to main.

Acceptance criteria:
- Page appears in User Guide navigation.
- Content distinguishes implemented behavior from limitations.
- Bot token/security notes are included.
- docs.json remains valid JSON.

Verification required:
- Validate docs.json.
- Run mint validate if CLI is available.
- Provide commit hash and expected public URL.
```

## Weak example

```text
Make Telegram docs better.
```

This is weak because it does not say:

- which docs,
- what audience,
- what content is missing,
- what should be published,
- what proof is needed.

## Make the task small enough to finish

Prefer one deliverable per task.

Good:

- "Write the User Guide page for Telegram bind."
- "Add workspace setting for Telegram user ID."
- "Verify Telegram bind live with one test bot and screenshot proof."

Risky:

- "Finish Telegram integration."
- "Make AgentDesk ready for Telegram users."

Large tasks hide missing requirements. Split them into smaller tasks with clear proof.

## Be explicit about verification

Agents should not mark important work done just because code was written.

Use concrete proof requirements:

- **UI work**: browser-based E2E test and screenshot proof.
- **Backend/API work**: unit/integration tests plus request/response examples.
- **Docs work**: published page path, nav entry, commit hash, and validation result.
- **Data/report work**: source files, method, output file, and review notes.
- **Live system work**: exact environment, account/profile used, timestamp, and observed result.

<Note>
For user-facing Dashboard behavior, prefer visible UI proof over DOM-only, API-only, or log-only proof.
</Note>

## Include boundaries

Clear boundaries prevent accidental scope creep.

Examples:

- "Do not change authentication."
- "Do not restart the gateway without approval."
- "Do not send external messages; dry-run only."
- "Do not mark PASS unless Playwright screenshot exists."
- "Do not reopen TASK-006 unless the regression is proven inside TASK-006 scope."

## Include exact identifiers

Use exact identifiers when they exist:

- Task id: `TASK-073`
- Subtask id: `SUB-7304`
- File path: `user-guide/telegram-bind.mdx`
- URL: `https://docs.agentdesk.team/user-guide/telegram-bind`
- Agent: `Nam`
- Workspace: `huy`

Exact identifiers reduce ambiguity and make handoff easier.

## Say what success looks like

A strong acceptance criterion is observable.

Weak:

```text
The page is good.
```

Strong:

```text
The User Guide page explains prerequisites, bind steps, error states, limitations, and the expected public URL; docs.json is valid; commit hash is provided.
```

## When requirements are uncertain

If you are not sure yet, ask the agent for analysis/spec first instead of implementation.

Example:

```text
Analyze options for adding workspace-level Telegram user ID setup. Write a short spec with recommended UX, API changes, risks, and acceptance criteria. Do not implement until approved.
```

This keeps unclear work out of execution.

## Task creation checklist

Before assigning a task, check:

- [ ] Title starts with an action.
- [ ] Goal is user/business outcome, not only technical activity.
- [ ] Scope and out-of-scope are clear.
- [ ] Inputs/references are attached or linked.
- [ ] Expected output is named.
- [ ] Acceptance criteria are testable.
- [ ] Verification method is explicit.
- [ ] Owner/reviewer is known.
- [ ] Task is small enough to complete and verify.
