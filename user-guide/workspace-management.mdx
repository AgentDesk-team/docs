# Workspace management

A workspace owns its agents, project/task records, sessions, files, connections, entitlements, and runtime. Administrative controls are available according to your role.

## Administration map

| Area | Purpose |
| --- | --- |
| **Agents in Agent Chat** | Profiles, context files, model overrides, availability. |
| **Model Providers** | Provider connections and workspace/agent model policy. |
| **People / Members** | Membership, invitations, roles, and groups. |
| **Usage** | Token activity, estimates, reported costs, and provider allowance. |
| **Analytics** | Reported workspace participation and usage telemetry. |
| **Billing** | Plan, seats, checkout, portal, and access recovery. |
| **Workspace settings** | Runtime status, audit, and permitted maintenance controls. |
| **Environments** | Read-only environment/port/deployment ownership when enabled. |
| **Skills** | Reusable capability management, covered at a high level. |

## Inspect before acting

Review current workspace identity, runtime readiness, health, available concurrency, recent audit, and any current operation. Some controls are restricted to platform operators or only offered in a supported runtime.

**Max active tasks per agent** limits live task assignments held by one agent. **Max runtime runs per workspace** limits simultaneous agent runs across agents and chats. Change the intended field within its displayed bounds and use its Save control. Increasing a task limit can increase runtime queueing; it does not create more provider capacity.

## Runtime and maintenance

Where available, **Restart workspace Gateway** is a maintenance action on the agent runtime. Inspect active work and review the confirmation before using it. Afterward, check readiness and the affected feature.

Dashboard or development-server restart controls are deployment/operator-specific. They are not a universal recovery step for normal users, and a restart should not be the first response to a missing file or an unapproved task.

A source update, provider save, runtime activation, and working feature are separate outcomes. Check the relevant status after a change.

## Audit and environments

**Support trail** lists recent workspace provisioning and support events. Expand event details or use **Export debug snapshot** when offered to assemble support information. Audit records help identify who changed settings and when. Review exported material before sharing it and exclude secrets from notes or support reports.

**Environments** shows read-only task/worktree/branch truth, port ownership, capacity, waiting work, and deployments. It can remain unavailable until the registry accuracy gate is enabled. Viewing an environment does not authorize deployment or runtime changes.

## Dangerous actions

Workspace deletion and other destructive controls require their explicit confirmation and authorized access. Inspect the exact workspace and understand the affected data before continuing.

Deletion is separate from archiving a project, pausing an agent, or removing an attachment reference. Use the smallest action that matches your intent.

## Platform administration

Platform Admin is restricted to platform-authorized accounts; workspace ownership alone does not grant it. Its operational controls are not ordinary user setup steps.

For routine administration, use the guides linked above rather than operator routes or internal configuration edits.
